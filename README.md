# Cosmos Attendance

Mobile-friendly attendance for Cosmos Engineering Solutions.

**Selected scope:** face matching with GPS; check-in from anywhere; employee management, check-in/out, daily attendance and monthly CSV exports. No payroll, leave, overtime rules or daily work reports.

## Status

## Architecture

- GitHub: application source and deployment configuration.
- Render: Python 3.11 Docker service running Flask/Gunicorn. Docker provides the C++ compiler and CMake needed to build dlib. Initial builds can still take several minutes.
- Neon PostgreSQL: employee profiles, hashed passwords, encrypted face templates, attendance timestamps and GPS coordinates.
- Cloudinary: authenticated (non-public) registration and attendance photographs. No face images or database records are saved on Render's ephemeral disk.
- Browser: device camera and one-time geolocation requests over HTTPS; no continuous location tracking.

The app compares a captured face against the **signed-in employee's** registered template on the server. It does not search strangers or identify people across unrelated datasets. Admins must supervise enrolment and confirm the employee's identity.

## Deploy, step by step

### 1. Put this project on GitHub

Create a **new private repository**, for example `cosmos-attendance-online`. Upload the contents of this folder, with `app.py`, `Dockerfile` and `render.yaml` at the repository root. Do not overwrite your previous attendance project. Never upload `.env`, actual passwords, employee photographs or database files.

### 2. Create a Neon database

Use a dedicated new project/database for this application. Copy the PostgreSQL connection string from Neon. Retain its SSL parameters. Set it as `DATABASE_URL` in Render. Initial tables are created automatically; existing unrelated databases should not be used.

### 3. Connect Cloudinary

In your Cloudinary account, obtain the `CLOUDINARY_URL` value shown with your API credentials, in the format `cloudinary://API_KEY:API_SECRET@CLOUD_NAME`. Add it to Render's environment. Keep it server-side. The code uploads all images with `type='authenticated'`; it does not expose public image URLs. Verify this access mode with your Cloudinary account before onboarding employees.

### 4. Generate and keep your secrets

Generate `SECRET_KEY` locally using Python:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Generate `FACE_ENCRYPTION_KEY` after installing the `cryptography` Python package:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Save the encryption key in a password manager. Keep it unchanged across deploys: losing it makes existing face templates unreadable. Changing it requires a migration or re-enrolling every employee. Store both keys only in Render's environment, not in GitHub or chat.

### 5. Create the Render service

In Render, use **New → Blueprint**, connect the new GitHub repository and let Render read `render.yaml`. Alternatively, create a Web Service with the **Docker** runtime from that repository. The Dockerfile controls Python; there is no `pip install` build-command override to enter.

Set these environment values:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Neon PostgreSQL URL, with SSL enabled |
| `CLOUDINARY_URL` | Cloudinary server credentials URL |
| `SECRET_KEY` | Random secret, 32+ characters; generated by Blueprint if used |
| `FACE_ENCRYPTION_KEY` | Fernet key generated above |
| `ADMIN_USERNAME` | `admin`, or your preferred admin login ID |
| `ADMIN_PASSWORD` | Unique password, at least 12 characters |
| `TZ_NAME` | `Asia/Kolkata` |
| `FACE_THRESHOLD` | Optional; defaults to `0.48` |

The Blueprint defaults to the free service plan. Face processing is CPU/RAM intensive: test your chosen instance with real staff; no free-tier performance guarantee is made. Review paid-plan costs before any upgrade. The default process uses one worker and two threads. Do not increase the worker count or scale instances without moving rate limiting to shared storage.

The health check is `/health`. On first startup, `init_db.py` creates the empty tables and first admin. Later restarts preserve Neon data. `ADMIN_PASSWORD` does not reset an existing administrator's password.

### 6. Onboard and test

1. Open the Render **HTTPS** URL on your phone and sign in as admin.
2. Open Employees → Add employee. Assign an ID and a unique password of 12+ characters.
3. With the employee present, open Register face. Explain what is stored and obtain their agreement. Capture one well-lit, front-facing photo.
4. Sign out. Sign in as that employee. Allow camera and location permissions, then check in.
5. Check out and confirm both timestamps, GPS coordinates and working hours in the admin daily view.
6. Export the month and check the CSV in Excel.
7. Redeploy once and verify records and enrolments are still present.
8. Test a non-matching person and poor/no-face photos. Confirm they are rejected. Check several real employees in varied lighting before relying on the threshold.

## Attendance rules

- A user must sign in with an active employee account and have an admin-registered face.
- Face matching happens on the server. The frontend cannot submit its own success result.
- GPS must be supplied for both check-in and check-out. Any location is allowed; there is no geofence. Accuracy in metres is recorded and visible.
- Server time is authoritative; working dates and reports use `Asia/Kolkata` unless configured otherwise.
- One shift per employee per local calendar day. No split shifts or break deductions in this version.
- An open shift can be checked out after midnight. The entire shift is assigned to its check-in date and month.
- There is no automatic checkout. An employee who forgets checkout must contact the administrator; attendance correction UI is outside the selected basic scope.
- Duplicate shifts are prevented by a database uniqueness constraint and employee row locking. Successful capture challenges cannot be reused.
- Employees can read only their own attendance. Admins can manage employees and export team records.
- Deactivation blocks sign-in and existing sessions. Employees with an open shift must check out first.
- Times in CSV are explicitly labelled with the company time zone. Open shifts have blank hours.

## Security and limitations

Passwords are hashed with Werkzeug; face templates are encrypted with Fernet. Session cookies are secure/HTTP-only in production. Write requests need a CSRF token; browser permissions request camera/location only for attendance. Images are re-encoded before upload, stripping metadata. Stored faces and photos never appear in API record responses. CSV text is escaped against formula injection.

**Face recognition is not liveness detection.** A photograph, replay or client modification may fool this basic flow. A short-lived server challenge reduces simple API replay but does not prove a live human is present. Device GPS can also be spoofed. Do not describe this release as tamper-proof or use it as the sole basis for adverse employment decisions. Higher assurance requires a separately evaluated liveness system and operating process.

The capture threshold requires real employee testing; both false matches and false rejections are possible. There is no production bypass that accepts an unverified face if processing fails. Camera/GPS and cloud-service errors prevent attendance from being recorded and are shown to the user.

Before live use, decide who can access employee data, how long to retain photographs/templates/GPS records, how deletion requests are handled, and how database backups are managed. This version has no automated retention job. Removing an employee's records requires a controlled database operation and deletion of the corresponding authenticated Cloudinary assets. Protect Neon, Render and Cloudinary administrator accounts. Failed database saves attempt to delete already-uploaded photos; if provider cleanup fails, an asset identifier is logged for administrator reconciliation.

The in-memory request limiter is designed for the single process in the Dockerfile. It resets on restart and is not distributed. There is no MFA or password-reset email service. Use the trusted admin maintenance command below.

## Maintenance

Reset a password in a trusted Render shell:

```bash
python manage.py reset-password ces001
```

The command prompts privately and invalidates existing sign-ins. Use `admin` instead of `ces001` for the default admin account. Do not place passwords on the command line.

Changing `SECRET_KEY` signs everyone out. Do not change `FACE_ENCRYPTION_KEY` without planning migration/re-enrolment. Schema creation is for a new database; subsequent schema changes need explicit migrations, not just `create_all`.

## Local development and tests

Use Python 3.11 for consistency with deployment. Install CMake and a C++ toolchain before installing `requirements.txt`, or use Docker. Variables in `.env.example` are documented examples: the app does not automatically load `.env`; export your variables in the shell or set them in your IDE. For local-only testing, set `APP_ENV=development` and `DATABASE_URL=sqlite:///local.db`. Never use SQLite for Render deployment.

```bash
pip install -r requirements.txt
pip install pytest==8.4.2
python -m pytest -q
node --check static/app.js
```

The native dlib 19.24.6 and face-recognition libraries installed and imported successfully locally. A real detector smoke test correctly rejected a blank camera-sized JPEG with no face. Real-person matching accuracy remains untested. The API test suite passed all **9 tests** locally. It uses isolated SQLite and simulated face/storage adapters. It checks authorisation, CSRF, invalid GPS, face mismatch handling, failed upload rollback, duplicate shifts, overnight checkout, consent, deactivation, encrypted templates, single-use challenges and safe CSV output. It is not a test of recognition accuracy, PostgreSQL concurrency, real Cloudinary access, phone permissions or the complete Docker image. Browser and WebMCP runtime testing were unavailable in this build session.

## V2 authentication and admin upgrade (25 Sep 2026)

This copy adds the requested login and administrator controls while preserving the existing face + GPS attendance flow.

### Login
- Employees can sign in with Employee ID + exactly 4-digit PIN.
- After a PIN sign-in, an employee can register a device biometric/passkey using WebAuthn.
- Later, the employee enters their Employee ID and chooses **Use phone biometric / passkey**.
- WebAuthn supports platform authenticators such as Face ID, Touch ID, Android biometrics and Windows Hello when the browser/device exposes them.
- Raw fingerprints/Face ID are never sent to Cosmos; the server stores a WebAuthn public-key credential.
- The administrator account continues to use a strong password rather than a 4-digit PIN.

### Administrator controls
- Add employee with 4-digit PIN.
- Edit employee name, ID and department.
- Reset employee PIN.
- Register/re-register/remove attendance face.
- Reset all biometric/passkey credentials for an employee.
- Activate/deactivate employee.
- Permanently remove employee and that employee's attendance/credential records.
- Edit check-in/check-out timestamps.
- Delete attendance records.
- Server audit-log table records sensitive admin changes.

### Existing database upgrade
`init_db.py` calls SQLAlchemy `create_all()`, so deploying this version against the existing Neon database creates the new `webauthn_credentials` and `audit_log` tables without deleting the current employee or attendance tables.

**Important:** existing non-admin employee passwords are not automatically converted to 4-digit PINs. After deployment, sign in as administrator and use **Reset PIN** for each existing employee before they use the new employee login.

### Dependency
This version adds `webauthn==3.0.0` to `requirements.txt`.

### Deployment note
WebAuthn requires a secure context. Use the Render HTTPS URL. The credential is tied to the site's RP/domain, so changing to a different production hostname can require employees to register their biometric/passkey again.
